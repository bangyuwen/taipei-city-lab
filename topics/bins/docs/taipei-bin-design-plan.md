# 台北街頭與商圈垃圾桶：完整設計計劃

更新：2026-10-16。基準版本：`a03bdac4cedc820c27b9152dbeb4e61ad1d8dfd5`。

本計劃補齊「研究 → 需求 → 方案比較 → 設計選擇 → 完整設計成果 → 網站呈現」的工作。T1 是既有候選概念，尚未經同需求方案比較，不預先指定為最終推薦。

**本輪完成的是可執行計劃。** 下列設計成果、網站調整及實體工作仍須依序執行；計劃完成不代表設計定案、工程可製造或已上線。

## 1. 要交付的結果與範圍

設計一套適合台北街頭與商圈「行人隨身小量垃圾」的設施提案，交代其與資源回收、剩餘液體、家戶及商家垃圾的服務分工。讀者應能理解用途、選擇理由、構件與操作，也能指出尚待確認的條件。

最終設計包須包含：

- 可追溯的需求與證據表，含需求優先序、衝突及缺口。
- 服務同一需求的候選比較、現況基準及選擇紀錄。
- 一個有理由的暫選方案；如關鍵條件會改變結果，保留條件式選擇。
- 外觀、尺寸、剖面、構件分解、材質配色、標示、街景配置與完整操作圖。
- 與同版圖面一致的 Three.js 展示，以及可獨立閱讀的文字／靜態圖。
- 五段式公開設計故事，以及與未知事項對應的後續驗證交接。

範圍維持在垃圾箱題目與獨立垃圾桶網站。不擴增新國家、全市選址模型、付款、辨識、感測後台或壓縮系統。既有其他用途概念保留為服務比較資料。現勘、製造、工程簽認、採購、實體試辦及部署，各自保留其執行條件；本計劃不替它們產生完成紀錄或新增外部行動授權。

## 3. 先建立可追溯的需求

### 證據與決策的共同格式

每項需求使用 `R-xx`；每項設計選擇使用 `D-xx`。記錄：需求 → 來源／使用情境 → 設計回應 → 比較理由 → 對應圖面／操作 → 剩餘未知 → 可推翻選擇的條件。

證據狀態使用四種文字標籤：**來源事實、專案推論、設計假設、待現場確認**。另外保留來源發布日期、查閱範圍及適用情境。未知不填成零，不替未訪談的人撰寫引言，不以國外照片推算精確規格。

以下是本案的初始優先序，屬設計工作排序，尚未經現地參與者確認。P0 是設計不得略過的基本條件；P1 是主要比較項目；P2 是在基本條件成立後比較的品質。

| ID | 優先序／需求 | 設計包必須回答 | 驗證／證據邊界 |
| --- | --- | --- | --- |
| R-01 | P0／投放與分流完整 | 各類常見隨身物件可投哪裡；不收時有什麼明確去處 | 在地收受規則及實際服務尚須核對 |
| R-02 | P0／不同使用者能操作 | 站姿、坐姿、年長者、單手持物者的接近、辨識與投放 | 尺寸圖與視角不等於可及性實測 |
| R-03 | P0／通行與作業空間可辨識 | 關門占地、開門、移桶、輪椅接近與連續通行分開畫 | 現地尺寸、適用要求與設置許可待確認 |
| R-04 | P0／衛生與漏液有去向 | 遮雨、可能進水、殘渣、異味、動物接觸、漏液與洗滌處理 | 不宣稱防雨、防鼠或防臭已達標 |
| R-05 | P0／完整清運任務可說明 | 從停用、開門到轉運、倒空／換袋、清洗、復位的路徑 | 重量、推拉力、車輛接口及專業安全判斷待實測 |
| R-06 | P1／辨識與分類清楚 | 圖示、文字、入口與分類容器彼此一致，不只靠顏色 | 本地辨識與錯投結果待測 |
| R-07 | P1／可維修與替換 | 袋、內桶、門鎖、入口、外板的接近方式與替換關係 | 可採購規格、工具、備件及耐久待確認 |
| R-08 | P1／容量與巡收相容 | 容量選擇如何對應垃圾組成、尖峰與兩次巡收間隔 | 60 L 仍為目標；沒有量測就不宣稱足夠 |
| R-09 | P1／成本與責任完整 | 零件、安裝、清運、清洗、耗材、維修的成本項與承接角色 | 未報價欄位留未知，不以外國單價或舊試辦預算代填 |
| R-10 | P2／適合街景且值得探索 | 形體、比例、材質、配色與標示形成一致設計；動畫解釋構件 | 精緻度以可檢視圖面與動作判斷，不虛構喜好調查 |

## 4. 先把真實任務寫完整

設計前完成一張物件／情境表。每列須有「使用者意圖、容器或合法替代去處、桶上文字／圖示、清運去向、異常時回應、未確認條件」。不得只寫「不可投」就結束情境。

| 任務 | 必須設計的回應 |
| --- | --- |
| 面紙、小型一般包裝 | 找到入口、單手投放、不中途接觸不必要表面；可收物依在地規則核對 |
| 空瓶罐、已清空飲料杯 | 明確說明分類與同點回收或既有回收路徑；不可暗示 T1 一般垃圾內桶會自動分流 |
| 尚有飲料的杯子、帶殘渣餐盒 | 畫出剩餘物的處理順序；未確認接收單位時標示服務缺口，不編造附近店家承接 |
| 菸蒂 | 明確決定不收或另設適當獨立收受；不得讓仍燃燒物直接進入一般內桶；防火設計需專業確認 |
| 家戶袋裝垃圾、商家營業垃圾 | 標示與行人服務的界線、官方替代資訊；不以縮口宣稱能辨認或阻止所有混倒 |
| 滿桶、入口堵住、漏液、維修中 | 顯示停用／回報與已確認的替代服務；不演示繼續塞入、不製作假營運聯絡資料 |
| 雨天、單手持物、坐姿接近 | 同時看人、物件、傘／輔具、入口深度與旁人動線，不只看入口高度 |
| 清運與恢復使用 | 停投 → 開鎖並固定門 → 抽桶／取袋 → 移到收集設備 → 倒空／換袋 → 在有污水收集的服務地點清洗 → 復位鎖定 → 恢復投放 |

各候選採相同服務範圍。首輪比較先共用「一般行人垃圾＋獨立說明回收去處」的任務；是否同點配置回收容器另作共同條件，不讓某個候選靠少提供一項服務取得占地優勢。完整站點占地須計入選用的回收容器。

## 5. 用同一需求比較，重新判斷 T1

先繪製三個候選與一個基準的粗略圖，不先替全部候選製作高精緻 3D。候選是機構假設，不是已證明可製造的產品。

| 方案 | 初始配置 | 主要要比較的取捨 |
| --- | --- | --- |
| B0：既有設備基準 | 選一個可追溯的台北既有桶／服務；無法取得完整規格時明列未知 | 保留與局部改善的成本及效果；不能用猜出的現況襯托新方案 |
| A：T1 起始方案 | 內縮無使用者翻蓋入口、前門、帶輪防漏內桶 | 接觸需求、入口遮護、門前作業空間、轉運搬抬與輪組維護 |
| B：自閉入口變體 | 與 A 共用服務範圍與可比容器，改為自閉入口 | 接觸／操作力、卡物、清潔、夾點與遮護的交換；不能預設衛生性能更好 |
| C：標準內桶／推車接口方案 | 以可核對的既有內桶或收運容器為核心配置外殼、門與標示；若未找到相容品，保留接口概念 | 零件取得、轉運、整體尺寸與外觀的交換；不能預設標準品一定較便宜 |

A／B 是入口對照；C 是維護與轉運架構對照。首輪不展開全部排列組合；如果結果支持 B 的入口與 C 的容器相配，僅補一張組合修訂圖，記錄改動與新增疑問。

### 選擇方法

1. 在相同任務、服務範圍與候選場景下畫圖。容量、占地、開口或清運頻率不同時，並列差異；不把較小包絡當成等服務的優勢。
2. 逐項查 R-01 至 R-05。明顯無法滿足者先修正或淘汰；未知者標為條件式候選，不能填成通過。沒有現地資料時，可完成桌面設計，不能授權落地。
3. 對 R-06 至 R-10 記錄「較有利、較不利、相近、未知」與證據。首輪不使用虛構精確分數或任意加權總分。
4. 寫出暫選方案、至少一個實質代價、未選方案的理由，以及會改選的條件。設計團隊提出有理由的建議；使用者決定重大的服務範圍／風格取捨，管理與工程角色確認現地及技術條件。
5. 若關鍵資料可能翻轉選擇，保留兩條明確條件分支與下一項需取得的證據，不假裝已決出勝者。

T1 的 480 × 420 × 1100 mm、60 L、入口 220 × 143 mm／中心 825 mm、304 外板與原配色，全部進入 `D-xx` 決策表。逐項標示「保留、修改、待定」及理由；本計劃沒有替它們新增性能背書。

## 7. 公開頁面與 Three.js 交付規格

維持 `#design` 入口與全站導覽。設計故事最多五個主要閱讀區塊：

1. **台北需要解決什麼**：核心需求與優先序；來源與詳細情境可展開。
2. **我們比較了哪些做法**：同需求候選、取捨與未選理由；手機以相同欄位逐案堆疊。
3. **目前推薦哪個，為什麼**：暫選條件、總覽、主要代價，接同版 3D。
4. **把設計看完整**：圖面、材料標示、配置與完整任務；細節逐項展開。
5. **下一個要確認的問題**：最近的驗證關卡；原七階段流程保留為收合的後續路徑。

兩個初始操作是「試投一張面紙」及「看清運順序」。它們是理解入口，不代表產品只處理面紙；第 4 節物件表與其餘操作在相鄰的自由探索區可達。原四用途放入「其他服務類型」，清楚顯示目前模型屬於哪一類，避免不同概念搭配固定 T1 規格。

精緻度的可交付要求：形體與接縫有層次；金屬、塗裝及標示材質可分辨；光影不掩蓋入口或門片；鏡頭能看見操作結果；門、內桶與垃圾沿已說明的次序移動。沿用現有 Three.js，不另加物理引擎或製作所有候選的高精緻模型。

動作與狀態要求：

- 操作由訪客觸發；提供可重播／重設的完整路徑，並可暫停或逐步檢視較長的清運序列。
- 清運中停投，內桶回位後才能關門並恢復；連按、重設與切換方案不得留下互相矛盾的狀態。
- 結果旁只解釋當下的一個設計理由；分類回應依使用者選定物件的規則，不暗示感測辨識。
- 轉運設備未知時，用有標籤的流程圖交代待定接口；不憑空製作看似已確定的吊掛或傾倒機構。
- 鍵盤與按鈕可替代拖曳；減少動態偏好顯示相同意義的靜態狀態；WebGL／模組失敗仍能讀完整圖文並完成操作說明。
- 手機保持模型、操作與結果相鄰；不靠橫向捲動或懸停才理解方案。離頁／背景時沿用現有停止渲染機制。
