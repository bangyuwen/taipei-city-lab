# 有桶｜找回消失的垃圾桶（debug松 議題 #2 MVP）

> **研究的界線**：本工具支援安排查核；人流不是垃圾量，清冊列數不是現場可用桶數，尚不能推薦新增箱位。

> **本資料夾（taipei-city-lab `sites/youtong/`）**：移植自 [evachen0927/youtong](https://github.com/evachen0927/youtong) `beta` 分支 commit `c42a8d3`。唯一的程式差異是 localStorage 前綴：本份由 `config.js` 依網址路徑決定（`window.KP`），一律為 **`有桶tcl_`**，不與正式站 `有桶_`、beta 站 `有桶beta_` 共用鍵；下文提到的 `有桶_xxx` 鍵名在本份皆為 `有桶tcl_xxx`，`?reset=1` 也只清 `有桶tcl_` 開頭的鍵。本機預覽：在 repo 根目錄執行 `python3 -m http.server 8765`，開 `http://localhost:8765/sites/youtong/`。

**有桶**：幫行人找到最近的垃圾桶，也幫設點規劃排出「建議先去現場查核」的順序（查核優先序）。

線上版：https://evachen0927.github.io/youtong/ ・程式碼：https://github.com/evachen0927/youtong

官方題目的問題陳述：台北行人專用垃圾桶從近 3,000 組縮減到約 800 組。這個靜態網站把**街道清冊垃圾桶**、**YouBike 借還活動量**與**公車站位**放在同一張地圖上，讓規劃者在示範區（公館–大安）找出「人多但附近沒有垃圾桶」的缺口，並比較三種方案：

- **A 維持現況**：現有桶位與容量，作為比較基準。
- **B1 原位改善指引**（研究定義）：位置與容量都不變，只改善指示牌、地圖與清潔箱標示等資訊；指標與 A 相同，本工具不推估時間或垃圾量的改善，以文字說明呈現。
- **B2 容量／頻率（模擬）**：**有桶團隊加的模擬，不在研究 PRD 內**。桶位不動；熱點最近的桶容量 80→120 公升、清運 2→3 次/日，參數在 `config.js > scenarioB`。
- **C 同桶數挪一處**：總桶數不變；只從熱點 1 公里內挑一個桶（周邊 200m 活動量最低者）移到熱點旁。條件是原位置 600m 內不能有站點從「200m 內有桶」變成沒有（`config.js > scenarioC.noNewGapM = 200`）。

方案定義沿用研究團隊（taipei-waste-lab，bangyuwen/taipei-city-lab commit 42c14f8，PRD v0.5／D18；https://github.com/bangyuwen/taipei-city-lab/tree/42c14f8/sites/taipei-waste-lab）「A 現況／B 原位改善／C 同桶數微調一處」；B 拆成 B1（研究定義）與 B2（我們加的模擬）。

## 三個頁面
| 頁面 | 檔案 | 功能 |
|---|---|---|
| 設點規劃（主頁） | `index.html` | 開場數字（來自 `config.js`）、示範區查核優先序、點熱點看 A/B/C 指標對照與地圖變化，「採用」後存入 localStorage |
| 行人 | `pedestrian.html` | 只顯示現況。定位（拒絕時改用示範位置「捷運公館站公車站」，`config.js > fallbackLocation`，到最近的桶步行 102 m；可點地圖手動設定）、最近 1 個垃圾桶（卡片不顯示類別標籤；點地圖上其他桶可換目標）、Google Maps 步行導航、一步回報：卡片直接問「這桶滿了嗎？」——「滿了」寫入回報（地圖該桶變紅，清潔隊頁讀得到），「還能丟」不寫入；按下後原位顯示一行：示範區內的桶按「滿了」→「謝謝，已通知清潔隊」，其他情況（含示範區外的桶，清潔隊頁看不到）→「謝謝回報」，同一桶不再問（`有桶_asked_v1`，重設會清除）；回報後感謝文字旁有「取消」，用事件 id 撤回自己那一筆（撤回「滿了」時清潔隊頁的已回報滿／行人回報／必清一起解除），撤回後可再問，換到別的桶前都可取消。手機一開頁卡片收合（只顯示全寬「步行導航」＋把手），點把手展開，桌機預設展開；切換後重新 fit（左上留白＝頁首底＋60px）。頁首只有標誌、角色切換與 i；已移除圖層 chip 列，行人頁不載入 YouBike／公車站資料（設點規劃頁不變）。「備用垃圾桶」固定顯示（青色菱形 #1f8fa3，畫在一般桶與目標之下，不參與最近桶與導航；彈窗第二行「依景點、商圈推估的可能丟點，尚未實地確認」）。清運規則：時間早於該桶最近一次清運的回報（滿了／還能丟／「這桶問過了」記憶）不再計算，桶變回正常、可再問；清潔隊「復原」清運則恢復先前回報；需求回報不受影響。只顯示步行路網距離（全臺北市）；卡片不顯示行政區與桶數 |
| 清潔隊 | `crew.html` | 手機點把手或卡片標題收合／展開並重新 fit。單一頁面：依預測產生參考清運順序（給領班參考，不排班、不派工，全部為模擬）。上方時間 chip 開抽屜（平日／週末＋時間滑桿，預設「平日 10:00」「週六 15:30」），卡片分「規劃」（必清／順路）與「執行」（逐站回報收運量 空／半／滿／滿溢，可復原；回報會歸零並校正該桶產生量）。舊網址 `crew-route.html` 會自動導向 `crew.html`。 |

## 怎麼執行
```bash
cd trash-mvp
python3 -m http.server 8765   # 開 http://localhost:8765/index.html
```
靜態網站（HTML/CSS/原生 JS + Leaflet）＋ Firebase Realtime Database（即時同步；SDK 從 gstatic CDN 載入）；所有路徑都是相對路徑，可直接放到 GitHub Pages（repo 根目錄），已附 `.nojekyll`。Leaflet 已放在 `vendor/`，不依賴 CDN；**地圖底圖仍需網路**（OpenStreetMap）。

開場數字、示範區範圍、行人頁示範位置與方案參數都在 **`config.js`**，改這個檔案即可。

### 預測調度的計算（`forecast.js`，參數在 `config.js > forecast`）
- 每小時人流 `F(h)` = 桶 200m 內 YouBike 站該小時每日平均借＋還次數的**平均**（只用 YouBike）。平日 22 天、週末 7 天（2026-07，排除 7/10、7/11）。
- 每小時產生量 = `F(h)` × 0.997 公升（**假設，不是觀測到的垃圾量**；校準：示範區人流中位數的桶平日一天裝滿 3 次＝官方每日清運下限，3 × 120 ÷ 361.1，`calibrate_rate.py`）× 該桶校正係數。
- 填充度 = 自最近一次例行清運（假設 05:00／08:00／12:00／16:00）或手動清運起的累積量 ÷ 容量 120 公升。清運後歸零（舊版會在每次例行清運後再疊加 0–30% 模擬殘留量，已修正）。
- 優先順序 = 預計滿時間由早到晚。「必清」期限 = 下一次例行清運或收班 16:30（取較早者）；已過收班則為隔天上班 08:00（時間設定在 `config.js`）。預計在期限前滿、或已被回報滿的桶列為必清。
- 路線 = 「清運範圍」兩段切換內的桶：「快滿了以上」（預設，內部門檻 70）或「只清滿溢」（內部 100）；畫面不顯示數字，舊存檔的數字門檻會對應到最近的選項（≥85→只清滿溢），「只清滿溢」沒有站時顯示「目前沒有滿溢的桶」。分兩層（`routeOrder:'tiered'`）：第 1 層「必清」＝下一次例行清運或收班（16:30）前預計會滿，收班後則為隔天 08:00 前會滿；第 2 層「順路」＝其餘達門檻的桶。層內從出發點起在行車路網距離上走最近鄰；站號＝實際拜訪順序。**不做最佳化**。示範時間：平日 10:00 vs 週六 15:30（對照 ≥100% 桶數）。
- 「已清運＋回報滿度」：該桶歸零，校正係數 `k ← 0.7·k + 0.3·k·(回報% ÷ 預測%)`（限 0.2–5），標示「已校正」。
- **限制**：
  - 跨日預測沿用同一日型（平日接平日、週末接週末；週五不會接到週六）。
  - 在平日時段按「已清運」只影響平日的預測，不影響週末（反之亦然）。
  - 200m 內沒有 YouBike 站的桶不會累積（示範區 43 個桶目前都有，換區時可能出現）。
  - **平日通勤限制**：人流只用 YouBike 借還代理，平日早上通勤尖峰的借還量很大，但通勤者不一定在站旁丟垃圾。因此模型會高估平日上午：平日 10:00 有 12 桶（28%）≥70%、2 桶 ≥100%，和週六 15:30（12 桶 28%、6 桶 ≥100%）差不多。我們沒有加權修正（不做非通勤加權、不用任意係數），請把平日數字當上限看。
  - YouBike 有通勤尖峰，平日早上的預測量可能高於週末傍晚；這是交通活動代理的特性，不代表實際垃圾量。
- 示範對照（抽屜預設與深連結）：`crew.html?fc=1&day=wk&t=10:00`（平日 10:00，≥100% 2 桶）vs `crew.html?fc=1&day=we&t=15:30`（週六 15:30，≥100% 6 桶）。

### 事件格式（localStorage 快取＋雲端 `events`）
`{id, bin, kind:'full'|'level'|'clear', level, by:'行人'|'清潔隊', ts, ot, amount, amountPct}`（`ot`＝原始回報時間，離線補傳時用它判斷是否早於清運；有效時間＝`ot ?? ts`，舊規則拒收 `ot` 時用戶端自動不帶 `ot` 重送，並在上傳前丟掉早於清運的離線佇列）；預測調度回報另加 `predPct`（預測滿度）、`calib`（新校正係數）、`fcDay`（wk/we）、`fcMin`（滑桿時間，分鐘）。校正係數另存 `localStorage['有桶_forecast_v1']`；清潔隊回報收運量時 `amount` 為 `empty|half|full|overflow`，`amountPct` 對應 0／50／100／120。

需求回報格式（localStorage `有桶_needs_v1`＋雲端 `needs`）：`{id, la, lo, ts, reason:null|'general'|'other', note}`（note ≤40 字）。事件與需求回報都會同步到雲端；雲端紀錄另加 `c`（clientId，用於頻率限制），`ts` 由伺服器時間寫入，刪除為 `del:true`。

重建資料：`python3 aggregate_youbike_trips.py`（需先下載 2026-07 租借紀錄 ZIP 到 `/workspace/raw/`）→ `python3 prep.py`（需 shapely、pyproj）→ 路網 `python build_walk_city.py`（步行，全市；osmium extract -p 臺北市多邊形 → tags-filter w/highway）＋`python build_roads.py`（行車，示範區）（osmnx；先以 osmium 從 Geofabrik 臺灣 pbf 擷取示範區並篩選道路，指令見檔頭）。測試：`python test_mvp.py`（Playwright，桌面 1280×800＋手機 390×844）。行人頁：`[data-full]` 回報滿了、`[data-ok]` 還能丟；清潔隊頁用 `#card [data-amt]` 回報收運量。

## 哪些是真的、哪些是推估或模擬
| 項目 | 性質 |
|---|---|
| 垃圾桶、YouBike、公車站的位置 | **真實**開放資料（清冊不等於現場完整現況） |
| 垃圾桶類別（一般垃圾＋資源回收） | **真實（全市一致說明）**：清冊沒有逐桶類別欄位；依環保局全市說明「每組包含一般垃圾箱與資源回收箱各 1 個」（中時 2025-08-17、聯合報報導），行人頁每桶都標一般＋回收，`bin-category.js` 的 `binCategory()` 回傳 `simulated:false`。若日後有逐桶欄位會自動改用 |
| YouBike 借＋還次數 | **真實**紀錄的彙總，但當作人流時是**推估** |
| 公車每站停靠路線數 | **推估**（路線數不是上下車人數） |
| 捷運 2026-07 OD（設點規劃頁捷運圖層） | **真實紀錄彙總，不是垃圾量** |
| **交通活動量是人流的推估，不等於垃圾量** | — |
| 垃圾桶填充度、滿溢告警 | **模擬**（依桶編號固定產生；行人與清潔隊回報會覆蓋） |
| 回報／清運／需求回報（Firebase 同步） | **真實**：使用者實際送出的資料，即時同步到所有裝置 |
| 清潔隊出發點 | **模擬** |
| 每小時人流（預測調度） | **推估**：由交通活動推估——200m 內 YouBike 站 2026-07 每小時「每日平均借＋還次數」的平均（真實紀錄彙總，`footfall_hourly.json`）。**公車不納入**（路線數換算人流沒有可靠依據，故只用 YouBike） |
| 垃圾產生量（每次借還 0.997 公升） | **假設，不是觀測到的垃圾量**：用官方公開的每日清運頻率校準——環保局資料「每個容量約 120 公升」「每日巡查清運頻率約 3 至 6 次」（聯合報 2025-08-17，經濟日報轉載 https://money.udn.com/money/story/7307/8944421 ）。假設示範區人流中位數的桶平日一天裝滿 3 次：3 × 120 ÷ 361.1 = 0.997 公升／次（`calibrate_rate.py`） |
| 例行清運時間 05:00、08:00、12:00、16:00 | **假設**：例行清運時間 05:00／08:00／12:00／16:00 為假設；官方公開資料只提到一天 3–6 次，沒有公布時間。預測從最近一次例行或手動清運起累積 |
| 預測填充度、預計滿時間 | **模擬** |
| 校正係數 | 由清潔隊回報的實際滿度 ÷ 預測滿度，以 EMA（α=0.3）更新；存在 localStorage |
| B 方案模擬參數與滿溢假設（容量、清運頻率、每千次借還產生公升數） | **模擬／假設**，參數在 `config.js` |
| C 方案移桶 | **情境模擬**，不是實際設置（只在設點規劃頁比較，行人頁只顯示現況） |
| 距離 | 所有地圖距離判斷（行人頁、開場數字、查核優先序、門檻敏感度、A/B1/B2/C 指標）一律用**全臺北市步行路網距離**（點投影到最近路段，多源 Dijkstra；每分鐘 75 m）；清潔隊路線用**行車路網距離**。點離道路超過 150 m 無法對應路網時才退回直線並標示「直線（無法對應路網）」（目前 YouBike／公車站位 0 個）。到桶的距離用步行計算；半徑內的數量用直線計算。（半徑計數如 C 方案 200m 需求、B2 附近站點、預測集水半徑等維持直線。）研究 repo 用直線距離，對照數字見下。例：捷運公館站(2號出口) 到最近清潔箱直線 41 m，但要過羅斯福路，步行最近的是羅斯福路4段70號之1，約 180 m——直線會低估。路網為 OSM，可能缺斑馬線或巷弄細節 |

## 熱點與方案的計算方式
- 示範區：公館–大安矩形（`config.js > demoArea`），YouBike 站＋公車站位。
- 開場數字（`config.js > headline`）：**步行路網距離、只用街道清冊**。681 列中 1 列（第 654 列，文山區「指南路3段40巷8-4號對面停車場 (貓空公車壺穴站)-1」，經度欄為 `?121.595369`）座標無法使用，與研究 repo 相同處理（剔除），有效 680 列。步行 100m 內無清冊垃圾桶：YouBike 1,644／1,821 站（90.3%）、公車 3,129／3,460 站位（90.4%）（直線距離時為 1,546（84.9%）／2,983（86.2%））；1,821 站含 29 個未營運站（act=0；YouBike 站點快照 2026-10-19 23:11）。以下為直線距離對照：研究 repo 只計營運站（1,790，快照 2026-10-18），100m 內有桶 271 站＝無桶 1,519 站（84.9%）；我們用營運站 1,792 站重算 50／100／150 m 內有桶為 132／271／376 站，與研究 `sensitivity.csv` 完全相同。「近 3,000 組減到約 800 組」是官方題目的問題陳述，不是本工具的計算。
- 清潔隊路線：見上方預測調度。
- **查核優先序**＝2026-07 借＋還次數（全月 `activity_all`；排除 7/10–7/11 的值只用在每小時預測）×（步行到最近街道清潔箱的距離 − 門檻），只列步行距離超過門檻的 YouBike 站。代表建議先去現場查核的順序，不代表現場沒有桶。門檻可切 100／200／300 m（開場數字、排名、地圖範圍圈一起更新）。**敏感度**（步行）：第 1 名三種門檻都是捷運大安站(4號出口)（步行 1,045 m，直線 799 m）；100 m 與 200 m：大安站4、信義安和站4、大安站3、東門站5、大安站5；300 m：大安站4、大安站3、信義安和站4、大安站5、東門站5（同 5 站、順序微調）。直線距離時 100 m 前 5 名相同。研究團隊的錨點是每區活動量前 3（間隔 ≥300m），兩者並列參考（`anchors.csv`）。
- 步行 100m／200m／300m 內無清冊垃圾桶——公車站位（共 3,460）：3,129／2,828／2,553（直線：2,983／2,668／2,346）；YouBike（共 1,821）：1,644／1,444／1,237（直線：1,546／1,302／1,066）。
- 設點規劃頁（桌機 ≥1024px）：右側面板左緣 8px 拖曳把手可調寬度（320px～視窗 60%，存 `localStorage['有桶_plan_panelW']`）；手機點把手收合／展開。備用垃圾桶與行人頁同款青色菱形。
- 備用垃圾桶：原始 130 列，但只有 120 個不同座標（10 列與其他列座標相同），`bins.geojson` 保留 120 點（`source:'scenic130'`），不計入桶數。
- 指標（各方案相同）：示範區內 100m／200m 內無桶站數、站點到最近桶中位數、100m 內有桶的 YouBike 活動量與公車停靠路線數，以及熱點旁桶每日滿溢時數（模擬）。C 方案另列「原服務區損失」。
- 工具建議規則（**假設，可調整**，`config.js > suggestion`）：熱點 100m 內有桶→B1；C 可行且至少減少 1 個「100m 內無桶」站→C；否則 A。仍需現勘、步行路徑、權責與清運確認。
- 滿溢模擬假設（**假設，可調整**，`config.js > scenarioB`）：每月每 1,000 次借還 → 每日產生 5 公升垃圾（另加基本量 5 公升/日）；桶容量 ÷ 每小時產生量 = 裝滿時數，與清運間隔比較得出每日滿溢時數。
- 「人流最高 ≠ 最優先」（設點規劃頁比較卡；門檻預設 100 m，比較句依目前排名即時計算，200／300 m 時顯示「未列入」）：捷運公館站(2號出口) 全月借還 91,340 次最高，步行到最近清潔箱約 180m（直線 41m）：門檻 100m 時排查核優先序第 43（共 245 站），200／300m 時不列入；捷運大安站(4號出口)「步行到最近街道清潔箱 1,045m（直線 799m），待現場查核」，是查核優先序第 1，且 42m 內有備用垃圾桶（120 點名單：大安捷運站）——備用垃圾桶是場所約略位置，不是垃圾桶。
- 研究團隊 39 處觀察錨點（每區活動量前 3＋臺大校區 3 處，`anchors.json`）可在設點規劃頁開啟圖層；錨點是觀察點，不是新設桶位。

## demo 前重置
示範前要把雲端回報清乾淨時，由**工程端**執行管理員腳本（不是網頁按鈕）：

1. 向 Eva 取得 Firebase 服務帳戶金鑰：Firebase 主控台 → 專案設定 → 服務帳戶 → 產生新的私密金鑰（JSON）。金鑰不要放進 repo。
2. `cd scripts && npm i firebase-admin`（第一次）
3. 執行：
   ```
   GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json \
   DB_URL=https://youtong-529da-default-rtdb.asia-southeast1.firebasedatabase.app \
   node scripts/wipe-cloud.mjs --yes
   ```
   腳本清空 `events`、`needs`、`owners`、`proof`、`last`，並把 `meta/epoch` 改成伺服器時間。

各頁會比對 `meta/epoch`：和本機記錄不同時，自動清掉本機的回報、需求回報、待上傳佇列（以及「這桶問過了」記錄、預測校正），所以舊資料不會被重新上傳。清空時離線的裝置，重新連線後也一樣：佇列裡的動作帶著舊 epoch，用戶端會丟掉，規則也會拒絕（`e` 必須等於目前的 `meta/epoch`）。`meta` 只能讀、用戶端不能寫。

模擬器演練：`firebase emulators:start --only database --project demo-youtong`，再 `python3 test_wipe.py`。
